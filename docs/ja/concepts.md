# 基本概念

[English](../concepts.md) | 日本語

特定の手法に依存しない、swift-test-effectiveness の土台となるモデルです。テストの effectiveness とは何か、「テストが欠けている」とは何か、別々の手法がどう組み合わさるのか、なぜスコアではなく宣言単位の指摘を出すのかを説明します。このモデルの一部を埋める手法は、それぞれ [methods/](methods/) に説明があります。

## テストの effectiveness

*テストの effectiveness* とは、テストスイートが故障を検出する力のことです（Just ら 2014、Inozemtseva & Holmes 2014 で使われている用語）。このツールはテストスイートの effectiveness を宣言単位で見てフィードバックします。宣言ごとに、その宣言の故障を検出するための条件のうちテストが満たしていないものと、何をすべきかを示します。

## PIE モデル

Voas (1992) の PIE モデルは、テストが故障を検出するための条件を 3 段階に分けます。

| 段階 | 意味 |
|---|---|
| **E**xecution | 故障箇所が実行される |
| **I**nfection | プログラムの状態が汚染される |
| **P**ropagation | 汚染がアサーションまで伝播し、テストが失敗する |

3 つすべてが必要で、ある計測で分かるのはそれが対象とする段階のことだけです。**カバレッジは E しか測りません。** 戻り値を一切アサートしないテストは、カバレッジ 100% でも E を満たすだけで、何も検出しません。このツールがカバレッジで止まらない理由であり、各手法をどの段階を測るかで説明する理由でもあります。

## ミューテーション分析

E + I + P をまとめて測る標準的な方法がミューテーション分析（DeMillo, Lipton & Sayward 1978, *Hints on Test Data Selection*）です。プログラムを人工的に小さく壊し（ミュータント）、テストがそれを検出（kill）できるかを見ます。この方法の正当性は 2 つの仮説に支えられています。

- **Competent programmer hypothesis**：実際のバグは、正しいプログラムからの小さな逸脱である。
- **Coupling effect**：単純なミュータントを検出できるテストは、より複雑な故障も検出する。

Just ら (2014) は、ミュータントの検出と実バグの検出に統計的な相関があることを示しました。

変種によって壊し方が違います。通常の（演算子レベルの）ミューテーションは小さな局所的変更（`+` を `-` に、`<` を `<=` に）をたくさん作るので、細かいがコストが高い。極端ミューテーションはメソッド本体を丸ごと置き換えるので、粗いが安い。どちらも同じ仮説に立っています。

## 「テストが欠けている」の 4 つの意味

「このコードにはテストが欠けている」には、粒度の違う 4 つの意味があります。

| # | 意味 | PIE 上の欠落 | 検出手段 | 対処 | スコープ |
|---|---|---|---|---|---|
| 1 | 実行されていない | E | カバレッジ | テストを書く | 対象 |
| 1' | 直接呼ぶテストがない（偶発的に実行されるだけ） | E（意図） | テストからの静的呼び出しグラフ | その API を主語にしたテストを書く | 対象 |
| 2 | 実行されるが検証されない | I + P | ミューテーション分析（極端・通常） | アサーションを足す | 対象（主軸） |
| 3 | 入力空間が探索されていない | 部分的 | 通常のミューテーション、MC/DC、境界値分析、PBT | 境界ケースを足す | 対象外 |
| 4 | 仕様上の振る舞いが検証されていない | 仕様による | 仕様とテストの突き合わせ | 仕様に対応するテストを書く | 当面は対象外 |

1 と 2 は対処が違う（テストを書く／アサーションを足す）ので、出力では必ず区別します。

1' はカバレッジでは見えません。統合寄りのテストの深い呼び出し経由で実行されるだけの宣言は、カバレッジ上は「実行済み」ですが、その宣言の契約に責任を持つテストが存在しません。

3 は「欠けている」と静的に指摘できません。通常のミューテーション（関係演算子の置換など）が一部を拾います。4 には突き合わせる仕様が必要です。

## 3 つの列：referenced / executed / verified

対象とする意味は、宣言ごとの互いに独立した 3 つの列に対応します。

| 列 | 問い | 性質 | 手法 |
|---|---|---|---|
| referenced | この宣言を直接呼ぶテストがあるか | 意図・静的 | [テストからの静的な参照](methods/static-references.md) |
| executed | テスト実行中に通ったか | 事実・動的 | [カバレッジ](methods/coverage.md) |
| verified | その宣言の故障が検出されるか | 事実・動的 | [極端ミューテーション](methods/extreme-mutation.md)（粗い）、通常のミューテーション（細かい） |

どの手法で列を埋めても成り立つ規則：

- **列は 1 つの数値に合成しない**（[スコアを出さない](#スコアを出さない) を参照）。
- **食い違ったら、静的な推定より動的な証拠を優先する。**
- **`verified` は実行された宣言にだけ計算する。** どのテストも実行しない宣言の故障は必ず見逃されるので、調べても新しい情報は得られない。その宣言はすでに「実行されていない」に属する。
- **`referenced` は直接の参照だけを数える。** 推移的に辿るとほぼ全ての宣言に到達し、`executed` と同じ情報になってしまう。

### 列の組み合わせの読み方

| referenced | executed | verified | 状態 | 対処 |
|---|---|---|---|---|
| ✗ | ✗ | — | テストがない | テストを書く |
| ✗ | ✓ | ✗ | 偶発的に実行されるだけで、検証されていない | その API を主語にしたテストを書く |
| ✗ | ✓ | ✓ | 偶発的な実行だが、結果的に検証されている | 低優先。直接のテストがあると望ましい |
| ✓ | ✓ | ✗ | 呼んでいるが検証していない | アサーションを足す |
| ✓ | ✓ | 一部 | 振る舞いの一部しか検証していない | 結果ごとに検証を足す |
| ✓ | ✓ | ✓ | テストされている | なし |
| ✓ | ✗ | — | 参照はあるが実行されない（スキップ、条件付きコンパイル、モック注入） | テスト側を確認する |

### 漏斗としての手法

手法はコストの順に、漏斗のように並べます。安い手法が、その下の高い手法で実行すべきものを絞り込みます。静的呼び出しグラフはテストの実行が不要、カバレッジは 1 回、ミューテーションはミュータントごとに 1 回です。そのため、手法を足すと解析は遅くなるのではなく、むしろ速くなる方向に働きます。

現在どの列と手法が使えるかは [README](../../README.ja.md#ドキュメント) に一覧があります。

## スコアを出さない

本ツールは **集計スコア（ミューテーションスコア、割合）を一切出力しません**。主出力は宣言単位の指摘と、次に何をすべきかの具体的なフィードバックです。理由は 2 つあります。

**スコアを裏付ける証拠がない。** Papadakis ら (2018, ICSE), *Are Mutation Scores Correlated with Real Fault Detection?* は、テストスイートのサイズを統制するとミューテーションスコアと実バグ検出の相関が弱まることを示しました。Inozemtseva & Holmes (2014) も、サイズを統制するとカバレッジと effectiveness の相関が強くないことを示しています。

**Goodhart の法則。** スコアを目標にすると、人間でも AI エージェントでも「スコアだけを上げる」最適化（アサーションの水増しなど）が起きます。「`isPositive(_:)` が常に `true` を返してもテストが落ちない。`false` になるべきケースを追加せよ」という指摘は、満たす方法がテストの改善しかありません。

同じ理由で、列も合成しません。ある手法で加点し別の手法で減点するような数値は、各手法が何を見つけたのかを隠してしまいます。

## 関連研究

- **Checked coverage**（Schuler & Zeller 2011）：アサーションから動的スライスで遡り、アサーションに影響する文だけを数える。オラクルの質を直接測る手法だが、Swift で動的スライスを取るのは現実的でない。
- **オラクルギャップ**：カバレッジとミューテーション検出の差。列で言えば、実行されているが検証されていない宣言の集合に当たる。
