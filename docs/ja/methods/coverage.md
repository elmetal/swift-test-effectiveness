# カバレッジ

[English](../../methods/coverage.md) | 日本語

**executed** 列（[基本概念](../concepts.md) を参照）を埋める手法です。そもそもどれかのテストがこのメソッドを実行したかを調べます。

## 何をするか

カバレッジは自前で計測しません。`swift test --enable-code-coverage` が出力する `llvm-cov export` の JSON を読み、その中の関数を、メソッド本体の開き括弧 `{` の位置で発見済みのメソッドに対応付けます。

結果は 2 つの用途に使います。

1. どのテストも実行しないメソッドを `not-covered`（PIE の E が不成立）として報告する。これは `pseudo-tested` とは別の問題で、対処も違う（アサーションを足すのではなく、テストを書く）。
2. 実行されないメソッドを、verified 列を埋めるより高コストな手法の対象から外す。一度も実行されないコードの故障は検出しようがないので、調べても時間がかかるだけである。

## カバレッジが使えないとき

| 状況 | 振る舞い |
|---|---|
| `--no-coverage` | カバレッジを取得しない |
| カスタムモード（`--build-command` / `--test-command`） | カバレッジを取得しない |
| カバレッジデータを読めない・解析できない | メッセージを出し、カバレッジなしとして扱う |
| データ中に対応する関数がないメソッド | そのメソッドを不明として扱う |

いずれの場合も executed 列は不明になり、verified 列の手法は該当する全メソッドに対して実行されます。その結果、どのテストも実行しないメソッドは `not-covered` として報告されず、検証で不合格になります（たとえば極端ミューテーションでは `pseudo-tested`）。カバレッジが使えたかどうかはレポートに表示されます。

## 限界

- カバレッジは *偶発的な* 実行も実行済みとして数える。統合寄りのテストの深い呼び出し経由で実行されるだけのメソッドは、責任を持つテストがなくても `executed` になる。`referenced` 列はこれを見えるようにするためのもの（[基本概念](../concepts.md#テストが欠けているの-4-つの意味) を参照）。
- 条件付きコンパイル、プラットフォーム分岐、非同期の実行タイミングによって、実行ごとにカバレッジがぶれることがある。
