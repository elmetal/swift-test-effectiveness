# テストからの静的な参照

[English](../../methods/static-references.md) | 日本語

**referenced** 列を埋めます（[基本概念](../concepts.md) を参照）。この問いに答える列です：このメソッドを直接参照するテストはあるか。

## 何をするか

この列が示すのは実行ではなく意図です。カバレッジから分かるのは、メソッドが実行されたことだけです。そのメソッドを対象にしたテストがあるのか、別のもののテストから呼ばれて実行されただけなのかは分かりません。referenced 列はこれを、何も実行せずにソースだけから判断します。

ツールは、ビルド時にコンパイラが書き出すインデックス（`swift build --enable-index-store`）を読みます。インデックスには、すべての参照がシンボル解決済みで記録されています。オーバーロード、extension、protocol メンバーの背後にある準拠は区別されます。

テストがメソッドを直接参照していれば、そのメソッドは **referenced** です。ここでいう「テスト」は次の 2 つです。

- **テストのスコープ**。次のどれかです。
  - `XCTestCase` のサブクラス
  - `@Suite` の付いた型、または `@Test` 関数を持つ型
  - トップレベルの `@Test` 関数

  型とその extension は 1 つのスコープとして扱います。そのため、`setUp()` で作った対象を `testXxx()` で使う書き方も参照に数えます。
- **スコープから呼ばれるテストターゲットのコード**。`makeSUT()` のようなヘルパー、モック、自前のアサーションなどです。これらはテストの一部なので、辿れるところまで辿ります。

本番コードの中は辿りません。テストが `a()` を呼び、`a()` が `b()` を呼ぶ場合、テストが参照しているのは `a()` だけです。推移的に辿ると、ほぼすべての宣言に到達してしまい、カバレッジと同じ情報になります。

## protocol やスーパークラス経由の呼び出し

テストが protocol 経由（`let repo: any Repository`）や override 可能なクラスメソッド経由でメソッドを呼ぶと、どの実装が動くかはコンパイラにも分かりません。

ツールは、この呼び出しを *rapid type analysis*（RTA）で解決します。ただし、見る範囲はそのテストスコープに限ります。

- 呼び出しは、スコープが名前を出している具体型それぞれの実装を参照したものとして扱います。名前が出ている場所は、テストコード自体でも、そこから呼ぶテストヘルパーでも構いません。
- クラスの場合は、その型自身の実装を参照したものとして扱います。自身の実装がなければ、最も近いスーパークラスの実装です。

| テストコード | referenced になる | ならない |
|---|---|---|
| `let repo: any Repository = SQLRepository(); repo.fetch(id: 1)` | `SQLRepository.fetch` | ほかの準拠型の `fetch` |
| `UserService(repo: MockRepository()).name(of: 1)` | `UserService.name(of:)` | 本物の `Repository.fetch` すべて |
| `repo.count()`（`SQLRepository` が protocol extension のデフォルト実装を使う場合） | デフォルトの `count()` | 自前の `count()` を持つ準拠型 |
| `setUp()` で `shape = Square(side: 2)`、テストで `shape.area()` | `Square.area` と `Shape.area`（呼び出しが名指ししている） | `Circle.area` |

この設計で重要なのはモックの行です。モックを注入したテストは本物の実装を動かしておらず、列もそのとおりに出ます。2 つの代替案はどちらもこれより悪くなります。

- 準拠型をすべて referenced にする方法（class hierarchy analysis）。モックを使うテストが、本物の実装を参照していることになってしまいます。
- どの準拠型も referenced にしない方法。protocol を使うテストがすべて、何も参照していないように見えます。

プロジェクトの外で宣言された protocol（`Equatable`、`CustomStringConvertible` など）の要件への呼び出しは解決しません。テストで値を文字列にしても、その型の `description` のテストにはなりません。

## 出力

解析した各メソッドの列は、JSON レポートに `referenced` として出ます。値は `"true"`、`"false"`、`"unknown"` のどれかです。次の場合は `unknown` になります。

- インデックスがない場合（下記参照）
- メソッドの行にあたる宣言がインデックスにない場合

テキストと Markdown のレポートでは、対処が変わる組み合わせにだけ注記を付けます（[列の組み合わせの読み方](../concepts.md#列の組み合わせの読み方) を参照）。

| 指摘 | referenced | レポートの注記 |
|---|---|---|
| `pseudo-tested`、`partially-tested` | false | どのテストも直接は呼んでいない。どこか別の場所にアサーションを足すのではなく、このメソッドを主語にしたテストを書く |
| `not-covered` | true | テストは参照しているが、実行されていない。スキップされたテスト、モックの注入、別の型へのディスパッチのどれか |
| `tested` | false | 間接的にしかテストされていない。優先度は低い |

この列は分類を変えません。静的な参照と動的な証拠を並べて報告し、指摘は動的な列で決まります。

## インデックスが使えないとき

| 状況 | 動作 |
|---|---|
| `--no-index` | インデックスを読まない。ビルドもインデックスを書かない |
| カスタムモードで `--index-store-path` がない | インデックスを読まない |
| インデックスストアや `libIndexStore.dylib` が見つからない、または開けない | メッセージを出し、列は unknown になる |

Xcode プロジェクトでは、カスタムのビルドコマンドが書き出すインデックスストアを `--index-store-path` で渡します。

- 相対パスは、ビルドコマンドが実行されるコピー先のプロジェクトを基準に解決します。
- 例：`xcodebuild` に `-derivedDataPath build` を付け、`--index-store-path build/Index.noindex/DataStore` を渡します。
- 宣言はパスで照合するので、インデックスはコピーをビルドしたときのものである必要があります。

`libIndexStore.dylib` は、`swift` 実行ファイル（`--swift`）のツールチェーンから読み込みます。そのため、インデックスの形式は書き出したコンパイラと常に一致します。

## 限界

- インデックスに残るのは、コンパイラが解決した参照だけです。静的に見えない呼び出しは数えません。`@objc` の動的ディスパッチ、セレクタ、文字列で渡すキーパス、リフレクションなどです。
- テストスコープは構文で見つけます。手がかりは次のとおりです。
  - 継承節の `XCTestCase`
  - `@Suite`
  - `@Test`
  - `testXxx()` メソッドを持つクラス（自前の基底クラスを経由して `XCTestCase` を継承している場合）
- スコープ内のどこかで名前が出た型は、そのスコープのすべての呼び出しに効きます。あるテストで `SQLRepository` を作り、別のテストでモックを注入するテストクラスでは、どちらのテストからも `SQLRepository.fetch` を参照したことになります。
- 基底クラス経由の呼び出しは、常に基底クラスのメソッドを参照したことになります。テスト内のインスタンスがすべて、そのメソッドを override したサブクラスであっても同じです。この場合、レポートには「参照されているが実行されていない」と出ます。これは実際の状況どおりです。
